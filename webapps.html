🎯 1. Introduzione alle Web Apps

Cosa sono le Web Applications?

Le web application sono applicazioni software accessibili tramite un web browser, che funzionano su server remoti e forniscono un'interfaccia interattiva agli utenti attraverso il protocollo HTTP/HTTPS.

🔑 Caratteristiche Principali

  • Accessibilità: Disponibili ovunque ci sia una connessione internet
  • Cross-platform: Funzionano su qualsiasi dispositivo con un browser
  • Aggiornamenti centralizzati: Non richiedono installazione sui dispositivi degli utenti
  • Scalabilità: Possono gestire un numero variabile di utenti
  • Manutenzione semplificata: Un'unica codebase da mantenere

Tipi di Web Applications

1. Static Web Apps

  • Contenuto fisso, uguale per tutti gli utenti
  • HTML, CSS, JavaScript statico
  • Hosting semplice e economico
  • Esempi: siti vetrina, landing pages

2. Dynamic Web Apps

  • Contenuto generato dinamicamente
  • Interazione con database
  • Personalizzazione per utente
  • Esempi: e-commerce, social networks

3. Single Page Applications (SPA)

  • Caricamento iniziale unico
  • Aggiornamenti dinamici via JavaScript
  • Esperienza fluida simile alle app native
  • Esempi: Gmail, Facebook, Twitter

4. Progressive Web Apps (PWA)

  • Funzionalità offline
  • Installabili come app native
  • Push notifications
  • Performance ottimizzate

🏗️ 2. Architetture Web

Client-Server Architecture

L'architettura fondamentale delle web app si basa sul modello client-server, dove il client (browser) effettua richieste e il server risponde con i dati richiesti.

Client (Browser) ←→ HTTP/HTTPS ←→ Web Server ←→ Application Server ←→ Database

Modelli Architetturali

1. Monolithic Architecture

  • Applicazione in un singolo blocco
  • Tutti i componenti strettamente accoppiati
  • Deployment unitario
  • Pro: Semplice da sviluppare e deployare inizialmente
  • Contro: Difficile da scalare e mantenere nel lungo termine

2. Microservices Architecture

  • Applicazione divisa in servizi indipendenti
  • Ogni servizio ha un proprio database
  • Comunicazione via API
  • Pro: Scalabilità, manutenibilità, tecnologie diverse per servizio
  • Contro: Complessità operativa, debugging distribuito

3. Serverless Architecture

  • Esecuzione event-driven
  • Nessuna gestione di server
  • Pagamento per esecuzione
  • Pro: Costi ottimizzati, auto-scaling
  • Contro: Cold start, vendor lock-in

Three-Tier Architecture

📊 I Tre Livelli

  • Presentation Tier: Frontend - interfaccia utente (HTML, CSS, JS)
  • Application Tier: Backend - logica di business (Node.js, Python, Java)
  • Data Tier: Database - persistenza dati (PostgreSQL, MongoDB)

Middleware e Autenticazione

Il middleware elabora le richieste prima che raggiungano le route handlers:

  • Logging delle richieste
  • Parsing del body (JSON, form data)
  • Gestione CORS
  • Autenticazione e autorizzazione
  • Rate limiting
// Middleware di autenticazione JWT
const jwt = require('jsonwebtoken');

function authenticateToken(req, res, next) {
  const token = req.headers['authorization']?.split(' ')[1];
  if (!token) return res.sendStatus(401);

  jwt.verify(token, process.env.SECRET_KEY, (err, user) => {
    if (err) return res.sendStatus(403);
    req.user = user;
    next();
  });
}

🔌 6. API REST e GraphQL

REST API

REpresentational State Transfer - architettura per API web basata su HTTP.

📐 Principi REST

  • Stateless: Ogni richiesta contiene tutte le informazioni necessarie
  • Resource-based: Le risorse sono identificate da URI
  • HTTP Methods: GET, POST, PUT, PATCH, DELETE
  • Status Codes: 200 OK, 201 Created, 404 Not Found, 500 Error

Struttura REST Endpoint

GET /api/users → Lista tutti gli utenti
GET /api/users/:id → Ottieni utente specifico
POST /api/users → Crea nuovo utente
PUT /api/users/:id → Aggiorna utente completo
PATCH /api/users/:id → Aggiorna parzialmente utente
DELETE /api/users/:id → Elimina utente

Best Practices REST

  • Usa nomi sostantivi per le risorse (non verbi)
  • Versiona le API (/api/v1/users)
  • Implementa paginazione per liste grandi
  • Usa HTTPS sempre
  • Documenta con OpenAPI/Swagger
  • Implementa rate limiting
  • Gestisci correttamente gli errori

GraphQL

Linguaggio di query per API, sviluppato da Facebook, alternativa a REST.

✨ Vantaggi di GraphQL

  • Query precise: Il client richiede esattamente i dati necessari
  • Un solo endpoint: /graphql per tutte le operazioni
  • Strongly typed: Schema definisce i tipi disponibili
  • No over-fetching: Evita il download di dati inutili
  • Introspection: Auto-documentazione e IDE support
# GraphQL Query Example
query {
  user(id: "123") {
    name
    email
    posts {
      title
      createdAt
    }
  }
}

# GraphQL Mutation
mutation {
  createUser(input: {
    name: "John"
    email: "john@example.com"
  }) {
    id
    name
  }
}

REST vs GraphQL

Aspetto REST GraphQL
Endpoint Multipli (/users, /posts) Singolo (/graphql)
Over-fetching Possibile Evitato
Versioning Necessario (v1, v2) Evoluzione schema
Caching HTTP caching nativo Più complesso
Curva apprendimento Più semplice Più ripida

🔒 7. Sicurezza Web

Vulnerabilità Comuni (OWASP Top 10)

1. Injection (SQL, NoSQL, Command)

  • Attacco: Inserimento di codice malevolo nelle query
  • Prevenzione: Prepared statements, input validation, ORM
// ❌ VULNERABILE
const query = `SELECT * FROM users WHERE id = ${req.params.id}`;

// ✅ SICURO (Prepared Statement)
const query = 'SELECT * FROM users WHERE id = ?';
db.execute(query, [req.params.id]);

2. Cross-Site Scripting (XSS)

  • Attacco: Iniezione di script nel browser dell'utente
  • Prevenzione: Sanitize input, escape output, Content Security Policy

3. Cross-Site Request Forgery (CSRF)

  • Attacco: Esecuzione non autorizzata di azioni per conto dell'utente
  • Prevenzione: CSRF tokens, SameSite cookies

4. Broken Authentication

  • Problemi: Session hijacking, password deboli, mancanza di MFA
  • Prevenzione: Password hashing (bcrypt), JWT, OAuth 2.0, MFA

Autenticazione e Autorizzazione

🔐 Strategie di Autenticazione

  • Session-based: Cookie con session ID, server mantiene sessione
  • Token-based (JWT): Token self-contained, stateless
  • OAuth 2.0: Delegazione autorizzazione (Google, Facebook login)
  • API Keys: Per integrazioni machine-to-machine
// Password Hashing con bcrypt
const bcrypt = require('bcrypt');
const saltRounds = 10;

// Hash password
const hashedPassword = await bcrypt.hash(password, saltRounds);

// Verifica password
const match = await bcrypt.compare(password, hashedPassword);

HTTPS e Certificati

  • Sempre usa HTTPS in produzione
  • Certificati gratuiti con Let's Encrypt
  • HSTS (HTTP Strict Transport Security)
  • TLS 1.3 per performance e sicurezza

Headers di Sicurezza

🚀 8. Deploy e Scalabilità

Ambienti di Deployment

Development

  • Ambiente locale degli sviluppatori
  • Hot reload, debug attivo
  • Database locale o di test

Staging

  • Ambiente pre-produzione
  • Replica della produzione

Production

  • Ambiente live per gli utenti

Piattaforme di Hosting

  • Google Cloud: Compute Engine, Cloud Run, Firebase - ML e data analytics
  • Azure: VMs, App Service, Functions - Integrazione Microsoft

Scalabilità

Scalabilità Verticale (Scale Up)

  • Aumentare risorse del server (CPU, RAM)
  • Limiti fisici
  • Più costoso

Scalabilità Orizzontale (Scale Out)

  • Aggiungere più server
  • Load balancer per distribuire il traffico
  • Richiede architettura stateless
  • Più flessibile e cost-effective

Monitoring e Logging

📊 Strumenti Essenziali

  • Monitoring: Prometheus, Grafana, Datadog, New Relic
  • Logging: ELK Stack (Elasticsearch, Logstash, Kibana), Loki
  • Error Tracking: Sentry, Rollbar
  • APM: Application Performance Monitoring
  • Uptime: Pingdom, UptimeRobot

Performance Optimization

  • Caching: Redis, CDN, browser caching
  • Compression: Gzip, Brotli
  • Database: Indexing, query optimization
  • Frontend: Code splitting, lazy loading, minification
  • Images: WebP, responsive images, lazy loading

💡 Best Practice: Implementa monitoring dal giorno 1. Non puoi ottimizzare ciò che non puoi misurare.
